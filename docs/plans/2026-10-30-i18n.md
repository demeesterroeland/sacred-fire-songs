## 1. Decision

Use the lightweight custom approach suggested in the issue (typed dictionaries + a pure `t()`), with one change: the locale is **request-scoped on the server** (cookie, then `Accept-Language`) instead of "always English on the server, swap after hydration".

| Option | Verdict |
| --- | --- |
| `next-intl` / `react-i18next` | Rejected: middleware + locale URL segments (`/nl/songs`) for a two-language UI, extra bundle and config. |
| Custom `t()`, server always English, client swaps from `localStorage` post-hydration (issue baseline) | Rejected as-is: Server Components can never switch (they never re-render on the client), Dutch users see an English flash on every load, and a module-level locale on the server would be shared between concurrent requests. |
| **Custom `t()` + locale cookie mirrored from `localStorage`** | **Chosen.** No middleware, no URL changes, full type safety, Server Components render the right language, hydration always matches. |

## 2. Architecture

| Piece | File | Role |
| --- | --- | --- |
| Dictionaries | `messages/en.ts`, `messages/nl.ts` | `en` is `as const`; `TranslationKey = keyof typeof en`; `nl` is `Partial<Record<TranslationKey, string>>`. |
| Engine | `lib/i18n/index.ts` | `tWithLocale()`, `interpolate()`, fallback (active → English → key), `resolveLocale()`, `resolveRequestLocale()`, `parseAcceptLanguage()`, cookie helpers, module-level `t()` for non-React code. |
| Server | `lib/i18n/server.ts` | `getServerLocale()` / `getServerT()` via `next/headers` (cookie → Accept-Language → English). |
| Browser persistence | `lib/i18n/persistence.ts` | DOM-free `readPersistedLocale()`, `persistLocale()`, `syncLocaleOnMount()`. |
| Provider | `context/LocaleContext.tsx` | Starts in the server locale; exposes `locale`, bound `t`, `setLocaleAndPersist`; refreshes Server Components until the layout locale matches. |
| UI | `components/common/navigation/LanguageSwitcher.tsx` | Sidebar footer (guests too), user menu, Account → Preferences → Language. |

Resolution order — browser: `localStorage` → cookie → `navigator.languages` → English. Server: cookie → `Accept-Language` → English. A browser-language default is never written to storage, so it keeps following the browser until the visitor makes an explicit choice.

## 3. Contributor rules

1. Add every new user-visible string to `messages/en.ts` **and** `messages/nl.ts` (the unit tests fail on missing keys, placeholder drift or empty values).
2. Server Component: `const t = await getServerT();` (make the component `async`).
3. Client Component: `const { t } = useLocale();` as the first hook; never call `t()` at module level (it would freeze the language at import time) — store a `TranslationKey` in config arrays and translate in render.
4. Keep the English copy identical when extracting existing strings (e2e specs select by visible text).
5. Do not translate song content (titles, lyrics, chords, artists, tags) or data values used in filters.

## 3b. Adding a language

1. Create `messages/<code>.ts` (copy the structure of `messages/nl.ts`; translate every key; keep `{placeholders}`).
2. Add the code to `Locale`, `SUPPORTED_LOCALES`, `LOCALE_LABELS` (own-language name), `LOCALE_DATE_TAGS` and `DICTIONARIES` in `lib/i18n/index.ts`; add browser aliases to `LOCALE_ALIASES` if needed.
3. Update the expected list in `testing/unit/tests/i18n.test.ts` and the Background of `docs/testing/i18n.feature`. The parity, placeholder and "not a copy of English" tests then cover the new file.
4. For languages with more than two plural forms (e.g. Russian) phrase count strings count-neutrally ("Песен: {count}").

Current languages: en (source), nl, es, it, ru, qu (Southern Quechua, machine-assisted, needs native review), fr, pt (Brazilian).

## 5. Out of scope / follow-ups

- Storing the language in the user profile (cross-device sync) — would need a `profiles.locale` column.
- Translating `app/manifest.ts`, `<title>` and meta description (static, English).
- Removing the unused starter components (`auth-button`, `logout-button`, `LibrarySidebar`, `home/SearchBar`, `YouTubeEmbed`, `forgot-password-form`, `update-password-form`) instead of translating them.
- About 100 dictionary keys are defined but unused (prepared during Phase 1); prune them once the UI settles.
