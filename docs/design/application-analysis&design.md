## 1. Introduction

### 1.1 Purpose
The purpose of this application is to centralize, preserve, and share the medicine songs (Icaros, ceremonial songs) of the Sacred Fire community. It serves as a digital songbook that bridges the gap between oral tradition and accessibility.

### 1.2 Scope
The application is a **Progressive Web App (PWA)** optimized for mobile use during ceremonies (dark mode, offline capable).
* **It IS:** A collaborative library for lyrics and chords.
* **It IS NOT:** A music streaming service.

### 1.3 Key Definitions
* **ChordPro:** A text-based format (`Example [Am]Chord`) used for rendering.
* **Song:** A "Composition" entity containing metadata (Title, Author).
* **Version:** A specific arrangement of a Song (e.g., "Capo 2", "Simplified").

## 2. User Analysis

### 2.1 User Personas
1.  **The Guitarero (Musician):** Needs accurate chords, transposition, and offline access.
2.  **The Singer:** Needs clear lyrics and melody reference.
3.  **The Guardian:** Ensures cultural respect and accuracy.

## 3. Functional Requirements

### 3.1 Song Library & Discovery
* **[Implemented] Lazy List:** Efficient fetching of song titles.
* **[Implemented] Search:** Real-time filtering by title, alias, songbook title, translated title, any author, category and lyrics (accents and case ignored; Stories 6.2.18, 6.2.23), narrowed by songbook and by language in the filter sheet (counts per option; Story 6.2.19).
* **[Planned] Taxonomy:** Filtering by Category (Water, Fire) deferred to later phases.

### 3.2 The Song Viewer
* **[Implemented] ChordPro Rendering:** Custom parser renders chords above lyrics.
* **[Implemented] Original and translation together (Story 6.2.14):** the reader switch *Original · Translation · Both* (songs with a translation); *Both* shows each stanza with its translation: side by side from md up, line under line on a phone; chords on the original only; `?lang=<tag>&view=translation|both`.
* **[Implemented] Language Switch (Story 6.2.13):** *Dutch · English* next to the reader switch, fed by `song_translations`; picks the language of *Translation* / *Both* (Story 6.2.14; two or more languages), shown under the version being read; picking a version returns to the original, `?lang=<tag>` deep link.
* **[Implemented] Version Switching:** UI pills to toggle between versions, named after their songbook (original, variants) or language (translations) and ordered original, variants, translations (Story 6.2.6).
* **[Implemented] Transposition:** (Foundation laid in logic, UI pending).

### 3.3 Offline Support
* **[Implemented] PWA:** Installable on mobile.
* **[Implemented] Caching:** `Stale-While-Revalidate` strategy via TanStack Query ensures songs work offline after first visit.
* **[Implemented] Offline fallback page (#353):** a page navigation without a connection shows a branded offline page in the visitor's interface language, with Retry and an automatic reload when the connection returns, instead of the browser's error page. Reading songs offline from a cache is not implemented yet (Story 4.5.1, second scenario).

## 5. Domain & Data Model (Implemented Codebase)

### 5.1 Schema: `public`

#### **A. compositions** (The Song Identity)
* `id`: uuid (PK)
* `title`: text
* `original_author`: text
* `owner_id`: uuid (FK -> profiles.id)
* `is_public`: boolean
* `has_chords`: boolean
* `has_melody`: boolean
* `catalog_slug`: text, unique when set, no surrounding spaces (stable external id of a song imported from a songbook catalog; Story 6.2.1). Set only by the service role or an admin (see 5.2)
* `aliases`: text[] (other titles; default empty)
* `authors`: text[] (every author; default empty. `original_author` stays the display text)
* `created_at`: timestamptz

#### **B. song_versions** (The Content)
* `id`: uuid (PK)
* `composition_id`: uuid (FK -> compositions.id)
* `version_name`: text (e.g., "Standard", "Capo 2"). The switch label when the version has no songbook and is not a translation; for a `translation` version it names the language (read by `translationLanguageTag`)
* `content_chordpro`: text (The raw lyrics/chords)
* `key`: text (e.g., "Am")
* `capo`: integer
* `soundcloud_url`: text (Renamed from audio_url)
* `youtube_url`: text
* `spotify_url`: text
* `contributor_id`: uuid
* `catalog_source_id`: text (external id of the version within its song, usually the songbook id; no surrounding spaces; unique per `composition_id`, so importers upsert on `(composition_id, catalog_source_id)`). Inserted only by the service role or an admin, updated only by the service role (see 5.2)
* `version_kind`: text, `original` (default) | `variant` | `translation`. Translations belong in `song_translations`; since the language switch (Story 6.2.13, #516) the app no longer reads a `translation` version as a language and migration `20261112140000` moves the interim ones
* `beats`: text, `song_note`: text (per-book musical data; key and capo use `key` / `capo`)
* `created_at`: timestamptz (versions are ordered original, variants, translations and within each kind oldest first, `id` tiebreak: `lib/songs/versionOrder.ts`. The default is the transaction start, so versions inserted in one transaction share it; importers set it explicitly)

#### **C. user_recordings** (Private Rehearsal Metadata)
* `id`: uuid (PK)
* `user_id`: uuid (FK -> profiles.id)
* `song_version_id`: uuid (FK -> song_versions.id)
* `recording_name`: text
* `storage_path`: text (Unique path in 'rehearsals' private storage bucket)
* `created_at`: timestamptz

#### **D. songbooks** (Printed source books, Story 6.2.1)
* `id`: text (PK, the book's stable external id, no surrounding spaces)
* `title`: text, `short_name`: text, `compiler`: text, `community`: text, `year`: integer
* `languages`: text[], `attribution`: text (licence or credit line)
* `created_at`: timestamptz

#### **E. song_version_sources** (Where a version was printed)
* `id`: uuid (PK)
* `song_version_id`: uuid (FK -> song_versions.id, cascade delete)
* `songbook_id`: text (FK -> songbooks.id, cascade update, restrict delete: a songbook that a source cites cannot be deleted; delete its sources first)
* `original_title`: text, `page`: text, `source_file`: text
* `is_primary`: boolean (at most one primary source per version). The song page shows the sources of the version being read under the lyrics (Story 6.2.10, #513), each linking to the book's page `/songbooks/<id>` (Story 6.2.11, #514).
* Unique `(song_version_id, songbook_id)`

#### **F. song_translations** (One translation per song and language)
* `id`: uuid (PK)
* `composition_id`: uuid (FK -> compositions.id, cascade delete)
* `language`: text (lowercase BCP 47-style tag such as `nl` or `pt-br`; `CHECK (language = lower(language))`)
* `title`: text, `lyrics`: text, `translator`: text
* Unique `(composition_id, language)`

#### **G. composition_redirects** (Old song links, Story 6.2.9)
* `old_id`: uuid (PK; the song that was linked as a version of another song, no longer in `compositions`)
* `new_id`: uuid (FK -> compositions.id, cascade delete): the song it lives in now. Linking that song again rewrites the rows that pointed at it, so a redirect never chains
* `catalog_slug`: text, unique when set: the linked song's catalog slug when the target kept its own (importers resolve it with `fn_song_id_for_catalog_slug`)
* `created_at`: timestamptz. Readable exactly when the target song is readable (RLS `EXISTS` on `compositions`: a guest finds the redirect to a public song, never one to a private song); written only by `fn_link_song_as_version`

#### **H. song_link_audit** (Who linked what, Story 6.2.9)
* `id`: uuid (PK), `actor_id`: uuid (FK -> profiles.id, set null), `source_id`, `target_id`: uuid (no FK, the row outlives both songs)
* `source_title`, `target_title`: text, `summary`: jsonb (what moved, as `fn_song_link_summary` returns it), `created_at`: timestamptz
* Readable by gatekeepers and admins; written only by `fn_link_song_as_version`

*(Categories and Setlists tables are designing but not yet implemented).*

### 5.2 Admin Access (Epic 3.6)
* **Role source:** `profiles.role` (`user_role` enum: `admin`, `gatekeeper`, `expert`, `musician`, `member`). Only `admin` may open `/admin/*`. "Musician status" in the admin UI means role `musician` or `expert`.
* **`public.fn_is_admin()`** (migration `20261009194500_admin_profiles_policy.sql`): `SECURITY DEFINER` helper returning whether `auth.uid()` has role `admin`, used in RLS without recursing into `profiles` policies.
* **Policies:** "Admins can read all profiles" (`profiles`, SELECT) and "Admins can view all setlists" (`setlists`, SELECT, so private playlists are counted and listed). Admins already read all `compositions` / `song_versions` via the existing admin-aware SELECT policies.
* **Queries:** `lib/admin/userQueries.ts` holds the queries with the Supabase client injected (`fetchAdminAccess`, `fetchAdminUsersList`, `fetchAdminUserDetails`); `lib/admin/serverQueries.ts` wraps them with the server client (`checkAdminAccess`, `getAdminUsersList`, `getAdminUserDetails`). Both list and detail queries return `null` for non-admin callers. Pure presentation logic (activity status, role labels, search/filter/sort, totals) lives in `lib/admin/userOverview.ts`.
* **Profile access:** a signed-in user reads their own full profile; an admin reads every profile. Guests have no row access to `profiles` and no privilege on `profiles.email`. The fields anyone may read (`id`, `full_name`, `avatar_url`, `is_musician`) come from the read-only view `public.public_profiles`, which also returns `role` to a signed-in caller (NULL for a guest; every member sees every role, Story 6.1.38); the app reads other members only through it, so no other member's e-mail address reaches the browser. User search (`search_users_for_sharing`) matches a name or a complete e-mail address and never returns an address. `user_recordings.singer_email` is readable only by the take's owner, through `own_recording_singer_emails()`.
* **Playlist item access (`setlist_items`):** readable when the parent playlist is public, owned by the caller, or the caller is admin. Writable (old and new row) through `public.fn_can_edit_setlist()`: owner, admin, or gatekeeper on a public playlist.
* **Profile writes:** a signed-in user changes their own profile fields (name, avatar, last seen). `id`, `email` and `created_at` change only in a trusted server context (service role, auth triggers), through the trigger `trg_guard_profile_fields`. `role` changes only there or through an admin. Signed-in users have no `INSERT` or `DELETE` privilege on `profiles`; `handle_new_user` creates a new profile with the default role `member`.
* **Category writes (`categories`):** admins insert, update and delete. Signed-in users may insert only artist sub-categories (`artist-*` under `artists`) and the `Artists` parent if it does not exist yet, because saving a song creates these through the user's session.
* **Playlist writes (`setlists`):** owners update their own playlists; admins and gatekeepers update public playlists, which stay public. `owner_id` is not updatable through the API (column privileges allow `title`, `description` and `is_public`).
* **Song version writes (`song_versions`):** insert requires `contributor_id` to be the caller and the caller to own the song or be admin (`public.fn_check_song_manage_access`). `composition_id`, `contributor_id` and `vote_count` are not updatable through the API. New editable columns need an addition to the column privileges; `version_kind`, `beats` and `song_note` are editable like `key` and `capo`. `catalog_source_id` has no update privilege for signed-in users (admins included; only the service role changes it), and the trigger `trg_guard_catalog_source_id` lets only the service role and admins insert a version with a non-null `catalog_source_id`.
* **Catalog slug (`compositions.catalog_slug`):** song owners may insert and update their songs, but the trigger `trg_guard_catalog_slug` refuses (SQLSTATE 42501) a non-null `catalog_slug` on insert and any change of it on update unless the caller is the service role (or another trusted database role) or an admin, so members cannot pre-claim an importer's key. `aliases` and `authors` stay editable by the song's owner.
* **Songbook data (`songbooks`, `song_version_sources`, `song_translations`, Story 6.2.1):** readable when the song is readable. The read policies only ask whether the linked `compositions` / `song_versions` row (or, for a songbook, a citing source row) is visible to the caller, so they follow those tables' rules automatically. Admins read and write everything; nobody else writes. Importers that upsert use the service role (see `docs/guides/importing-songbooks.md`).
* **Linking songs (Story 6.2.9):** `fn_link_song_as_version(source, target)` and `fn_preview_song_link(source, target)` are `SECURITY DEFINER` with `search_path = ''`, executable by `authenticated` only (the checks need `auth.uid()`, so a `service_role` call could only be refused; importers do not merge, they resolve slugs with `fn_song_id_for_catalog_slug`). Inside, `fn_assert_can_link_song` refuses callers who are not gatekeeper or admin (42501), the same song (22023) and a source that was already linked (22023); a song a gatekeeper cannot read (private, someone else's) is "not found" (P0002), and a gatekeeper who does not own both songs is refused (42501 *Gatekeepers can only link songs they own*); admins link any song. For everyone, admins included, both songs must have the same visibility (22023 *Both songs must be public, or both private*). `fn_link_song_as_version` checks again after it has locked both songs, so a link that lost a race reads "already linked". `composition_redirects` and `song_link_audit` have no write privileges for `anon` / `authenticated`.
* **Catalog corrections (Story 6.2.21):** the trigger `trg_track_catalog_edit` marks a catalog song or version (`edited_in_app`, `edited_at`, `edited_fields`) when a signed-in user changes a tracked column; API callers cannot set or clear the markers. Only signed-in admins may call `fn_catalog_edits_export()` and `fn_clear_catalog_edit()`; guests and the service role have no execute privilege (the functions check `fn_is_admin()`, which reads `auth.uid()`). Importers read and clear the markers with plain SQL as the service role. The trigger function `fn_track_catalog_edit()` is executable by nobody through the API (`service_role` included). See §6.20.
* **Global search filter counts (Story 6.2.25, #570):** `public.fn_search_filter_counts()` is a read-only `SECURITY INVOKER` (`SET search_path = ''`) SQL function executable by `anon`, `authenticated`, and `service_role`. Both its `songbook` branch (`songbooks` -> `song_version_sources` -> `song_versions` -> `compositions`) and its `language` branch (`categories` under `Languages` -> `song_category_map` -> `compositions`) explicitly join `public.compositions` so `compositions` RLS decides what each caller counts (necessary because `song_category_map` allows public read via `USING (true)`): guests count public songs only (books with no visible songs are omitted), members count public plus their own private songs, and admins count all songs.
* **Activity status:** `active` when `profiles.last_seen_at` is within 30 days, `inactive` when older, `never` when null.
* **Not modelled yet:** comments and flags (named as example contributions in Story 3.6.1) have no tables, so they are not shown.

### 6.2 Offline Strategy
* **React Query:** Configured with `staleTime: 1 minute` (default for lists) and `gcTime: 24 hours`. Detail queries may override to 5 minutes.
* **Browser Cache:** Assets cached via Vercel headers.
* **Service worker (`public/sw.js`):** on install it stores `public/offline.html` in the `sfs-offline-v<n>` cache (activate removes older versions). Its fetch handler answers only `GET` page navigations while `navigator.onLine` is false, with that page; everything else, and every request while online, is left to the browser (a pass-through fetch handler once broke online navigations). ### 6.3 E2E Testing Environment & Database Isolation

### 6.5 Internationalization (i18n)
* **Languages:** English (default, source of truth), Dutch, Spanish, Italian, Russian, Southern Quechua (Runasimi), French and Brazilian Portuguese. Codes `en nl es it ru qu fr pt`; browser tags `quz`/`quy` map to `qu`, `pt-BR`/`pt-PT` to `pt`; dates use `LOCALE_DATE_TAGS`. Quechua is machine-assisted and needs native review. Only the interface is translated; song content (titles, lyrics, chords, artists, tags) never is. Story 3.7.1 / issue #246; behaviour catalogue in `docs/testing/i18n.feature` (I18N-01 … I18N-10).
* **Dictionaries:** `messages/en.ts` (`as const`, `TranslationKey = keyof typeof en`) and one `Partial<Record<TranslationKey, string>>` file per language (`messages/nl.ts`, `es`, `it`, `ru`, `qu`, `fr`, `pt`), registered in `DICTIONARIES`. Count strings in Russian/Quechua use count-neutral phrasing because the engine only knows one/other. Keys are dot-namespaced per feature; placeholders use `{name}`. Unit tests enforce identical key sets, identical placeholders and no empty values.
* **Engine (`lib/i18n/index.ts`):** no third-party library, no middleware or locale URLs. `tWithLocale(locale, key, params)` interpolates and falls back active dictionary → English → the key itself (never blank). `resolveLocale()` picks the explicit choice (localStorage, then cookie) → first supported browser language (`navigator.languages` / `Accept-Language`, `nl-BE` → `nl`) → English; unknown values are ignored.
* **Server Components:** `const t = await getServerT()` from `lib/i18n/server.ts` reads the `sacred-fire-songs-locale` cookie, else `Accept-Language` (request-scoped, safe under concurrency). The root layout renders `<html lang>` with that locale and passes it to `LocaleProvider`.
* **Client Components:** `const { t } = useLocale()` (`context/LocaleContext.tsx`). The provider starts in the server's locale, so SSR and hydration match (no hydration mismatch, no English flash). After mount it re-reads localStorage/cookie/browser language (`lib/i18n/persistence.ts`); a browser-language default is never persisted. Switching writes localStorage + a 1-year `SameSite=Lax` cookie, updates `<html lang>` and refreshes Server Components until the layout's locale matches (bounded retries).
* **Language switcher:** `components/common/navigation/LanguageSwitcher.tsx` (WAI-ARIA listbox: trigger button + list portalled to `<body>` so it is never clipped; each language in its own name and script, sorted by that name; the active language marked by a lit ember "wick" that ignites once on selection, skipped under reduced motion; keyboard: arrows, Home/End, type-ahead, Enter, Esc; pure logic in `components/common/navigation/languageListbox.ts`) in the sidebar footer (also for guests), the user menu and Account → Preferences → Language. The choice is per device/browser (not stored in the profile) and survives reloads and sign-out.
* **PDF footer & cache (#303/#304):** bottom-left shows the site host and a 1 cm QR code to the page's song; repeated exports reuse the cached PDF (`lib/export/pdfCache.ts`) until the playlist content (including each song's key, capo, tuning, beats and sources, in a fixed order), language or site changes.
* **PDF export:** `exportPlaylistToPdf({ …, locale })` uses `getPdfLabels(locale)` (`lib/export/pdfExport.ts`) for page footer, song meta line (key, capo, tuning, beats, as on the song page, Story 6.2.17), source credit line, subtitle and date format; the UI passes the active locale. Song content in the PDF is untranslated (a translation is never printed); server-action error messages are shown as the toast description under a translated title.
* **Not translated:** `app/manifest.ts` and `<title>`/meta description (static, English); server action error codes; unused starter components (`logout-button`, `YouTubeEmbed`).

### 6.7 Client Auth State (`useAuth`, #321)
* **Server-seeded:** `app/layout.tsx` resolves the user on the server and passes it to `Header` / `UserProfile` as `initialUser` (`AuthUser` or `null` for a guest). With a server view, `useAuth(initialUser)` starts with `loading = false`, so the header never flashes.
* **Unseeded callers:** `useAuth()` without an argument (`initialUser === undefined`) starts with `loading = true` and only drops it once `getSession()` + profile resolve (5 s profile timeout, guest fallback). Client guards must wait for `!loading` before treating `user === null` as a guest.
* **Prefer server guards:** pages that require login check `supabase.auth.getUser()` in a Server Component and `redirect('/auth/login?next=<path>')` (`/library/playlists/add`, `/library/playlists/[id]`, `/library/recently-viewed`). `/auth/login` redirects an already-signed-in user to `next` (default `/`), so a client guard that fires too early bounces the user to the home page.
* **Tests:** `testing/unit/tests/useAuth.test.ts` (first-render state), `e2e/tests/playlist-add-auth.spec.ts` (logged-in user stays on the form, guest gets `next=`).

### 6.8 Private Song Sharing, DRM-lite & Singer Attribution
* **Data Model & Schema:** Extended `user_recordings` with `is_public` (boolean), `singer_consent_confirmed` (boolean), `singer_profile_id` (UUID references `profiles.id`), `singer_name` (text), and `singer_email` (text). Created join table `recording_shares` (`id`, `recording_id`, `shared_with_user_id`, `created_at`) with foreign keys cascading on delete. Performance indexes on `(recording_id, shared_with_user_id)` and lookup columns.
* **Strict Permissions & DRM-lite:**
  - Recording owners can manage sharing and revoke access. Non-owners (shared recipients) cannot share or reshare recordings.
  - Streaming playback is allowed for shared recipients via signed URLs or public access.
  - Downloads are strictly blocked for non-owners (`getRecordingDownloadUrl` rejects non-owners; client download buttons and controls are omitted for shared recipients).
* **Singer Consent Disclaimer:** Transitioning a recording to public visibility requires explicit user acknowledgement of singer consent via a confirmation modal (`RecordingPublishModal`), persisting `singer_consent_confirmed = true`.
* **Singer Attribution:**
  - Registered musicians: linked by `singer_profile_id` with verified badge and profile link (`/users/:id`; the profile shows the user's role badge, Story 6.1.38), displaying the attributed recordings the viewer may read. Each row plays the recording on the profile (signed URL from `fetchMusicianProfile`, routed through the same-origin `/supabase-api` proxy, shared `AudioProvider`, one at a time) and opens the song with that take (`recordingPermalink`); Story 6.1.37, #490.
  - Unregistered singers: handled gracefully with `singer_name` and pending invite status badge without breaking playback or navigation.
* **Supabase RLS & Storage Security:**
  - Storage bucket `rehearsals`: SELECT permits owner (`(storage.foldername(name))[1] = auth.uid()::text`), recipients with an active share in `recording_shares`, or public recordings.
  - Profiles: targeted RLS read policies permit reading singer attribution profiles and recipient identities without blanket profile exposure.
* **Tests & Quality:** Executable Gherkin spec `docs/testing/recording-sharing.feature`, step definitions `testing/bdd/steps/recording-sharing.steps.ts`, Vitest unit test suite `testing/unit/tests/recordingSharing.test.ts`, and full 8-locale key parity in `messages/*.ts`.

### 6.9 Share Notifications (Story 4.6.6)
* **In-app notifications:** `public.notifications` (`user_id`, `actor_id`, `type`, `recording_id`, `composition_id`, `metadata` jsonb, `read_at`, `created_at`). Rows are created only by the `security definer` trigger `fn_notify_recording_shared` on `recording_shares` INSERT; there is no INSERT policy. Errors in the trigger are caught and logged as WARNING, so a notification failure never blocks a share. Revoking a share deletes its notification (`fn_remove_recording_share_notification`). RLS: recipients read and delete their own rows; the only column they may update is `read_at` (column grant). `metadata` snapshots `actor_name`, `song_title` and `recording_name`; the UI renders the text with `t('notifications.recordingShared')`, so it follows the reader's locale.
* **Header bell:** (see also §6.15, Shared with me) `components/common/navigation/NotificationBell.tsx` (signed-in users) shows the unread count and the latest 20 notifications (`lib/notifications/queries.ts`). It refetches on window focus and every 60 s. Opening an item marks it read and goes to the recording permalink (`/recordings/:recordingId`); "Mark all as read" clears the badge.
* **Transactional email:** After a new share (not a duplicate), `shareRecording` calls the server action `sendRecordingShareEmail` (`lib/actions/notifications.ts`) fire-and-forget. The action reads the signed-in user and calls the `claim_recording_share_email` RPC with the server-only client `createAdminClient()` (`lib/supabase/admin.ts`, secret key, never the user's session; only `service_role` may execute it). The RPC sets `recording_shares.email_sent_at` and returns the recipient details only if that user (`p_owner_id`) owns the recording, the share has not been emailed yet and the recipient has `profiles.email_notifications = true`. That makes it idempotent and owner-only. Mail is sent with `after()` over SMTP (`lib/notifications/mailer.ts`, `nodemailer`). Failures are logged, never surfaced. Content: `buildRecordingSharedEmail` (`lib/notifications/email.ts`, `email.recordingShared.*` keys, HTML-escaped, default locale because profiles do not store a language yet). ### 6.19 Link a song as a version of another song (UX v3, Story 6.2.9, G1.4)
* **Who and where:** admins on every song and gatekeepers on the songs they own (`canLinkSong` in `lib/songs/linkSong.ts`; owner decision Nov 12, 2026) see ⋮ → "Link as a version of…" on the song page, on every width. The database enforces the same: a gatekeeper must own the source **and** the target. The sheet (`LinkSongSheet`) searches song titles (`searchSongsToLinkTo`, the song itself left out; a gatekeeper finds only their own songs, an admin every song they can read), then shows the preview: versions, recordings, playlist entries, favourites, shared favourites merged, new categories, translations, new other titles, the catalog slug outcome and versions that lose a songbook key. Lines with nothing to move are left out. A refusal (not their own, different visibility, already linked) shows in the preview, before any confirm; Confirm runs the link once even when clicked twice.
* **Same visibility:** a public song is never merged into a private one, or the other way round, for everyone (admins included): it would publish private versions and takes, or hide public ones. Make one of the songs public or private first.
* **Confirm, not undo:** the merge deletes the duplicate song and rewrites favourites, so an undo would have to restore many rows exactly. The sheet asks for a clear confirm with the preview and says it cannot be undone; `song_link_audit` keeps who linked what.
* **The merge** (`fn_link_song_as_version`, one transaction, both songs locked): the source's versions move to the target (an `original` becomes a `variant`, so the target's original stays first); recordings and playlist entries point at versions and follow. Categories and song views are merged, translations move (a language the target already has keeps the target's text, empty fields filled in), notifications are re-pointed. The target's `aliases` gain the source title and aliases (no duplicates, never its own title), `authors` are merged, `has_chords` / `has_melody` are or-ed. Favourites are per song: every "My Favorites" item of the target points at its first version again and a member who had favourited both keeps one.
* **Catalog keys:** the target keeps its `catalog_slug`, or takes the source's when it has none; otherwise the source's slug stays on the redirect and `fn_song_id_for_catalog_slug` resolves it to the target, so an importer does not re-create the source. A moved version whose `catalog_source_id` the target already has keeps its content but loses the key (unique `(composition_id, catalog_source_id)`). This deliberately bypasses the admin-only catalog guards (`trg_guard_catalog_slug`, `trg_guard_catalog_source_id`, §5.2): `fn_link_song_as_version` runs as its owner (`postgres`), which the guards treat as a trusted importer context, so a gatekeeper's link moves keys too (owner decision, Nov 12, 2026). The risk is low: the values only ever come from the source song (no caller input reaches a catalog column), so a link can keep an existing key reachable on the song that stays but never claim a new one.
* **Old links:** the song page asks `composition_redirects` when a song id has no song and replaces the URL with the target, keeping `?version=` and `?recording=` (the versions and takes moved along). An unknown id still shows the 404 page.
### 6.20 Catalog corrections protected from re-import (UX v3, Story 6.2.21, G5.4)
* **Problem:** an importer updates the catalog rows it owns on every run; a correction made in the app would be overwritten.
* **Marker in the database, not in app code:** `BEFORE INSERT OR UPDATE` trigger `trg_track_catalog_edit` on `compositions` and `song_versions` (one function, `fn_track_catalog_edit`, with the key column and the tracked columns as trigger arguments). It marks a row when it has a catalog key before or after the write (`catalog_slug` / the version's own `catalog_source_id`; removing the key counts as a change of that column), the request's JWT role (`auth.role()`) is `authenticated`, and a tracked column changed (`IS DISTINCT FROM`, compared through `to_jsonb`). Every app path (the song form, new edit-form fields, database functions) is covered without coordination.
* **Who counts:** signed-in users, also through `SECURITY DEFINER` functions they call (they run as `postgres`, but `auth.role()` is still the user's): linking a song as a version of another (#512, §6.19) marks the moved catalog versions (`composition_id`, `version_kind`; a version whose colliding `catalog_source_id` was cleared: `catalog_source_id`) and the target's merged names (`aliases`; `authors` / `original_author` when they gain something; `catalog_slug` when it took the source's slug). Not marked: the service role (importers) and sessions without a JWT role (data migrations such as `20261112140000`).
* **Tracked:** song `title`, `original_author`, `aliases`, `authors`; version `version_name`, `content_chordpro`, `melody_notation`, `key`, `capo`, `tuning`, `soundcloud_url`, `youtube_url`, `spotify_url`, `version_kind`, `beats`, `song_note`, `composition_id`. Not tracked: derived flags (`has_chords`, `has_melody`), `is_public`, `owner_id`, `vote_count`, `contributor_id`, sources and translations (admin-only tables), and deletions. The snapshots (`to_jsonb`) are built only after the cheap early returns (role, operation, catalog key). `edited_fields` accumulates (sorted union) until cleared. Inserts are never marked.
* **Song and version markers are separate:** a corrected title does not block new or untouched versions of that song.
* **No baseline snapshot:** the export carries the edited fields and their current values; the source catalog holds the old values. Simpler than storing the importer's last values, and enough to take a correction over.
* **Tampering:** for API callers (`current_user` `anon` / `authenticated`) the trigger restores the markers (defaults on insert); `song_versions` has no column privilege on them either.
* **Export and clearing:** `fn_catalog_edits_export()` (`SECURITY DEFINER`, admins only, 42501 otherwise) returns `{songs, versions}` with catalog keys (null when removed in the app), `edited_at`, `edited_fields` and `values` (for `composition_id`: the `catalog_slug` of the version's song now, not the internal id). `fn_clear_catalog_edit(kind, id, edited_at)` clears one marker only while its `edited_at` still equals the downloaded one and answers `cleared`, `changed` (corrected again since: still marked) or `not_marked`; the server action maps them, plus `forbidden` and `error`, to `{ ok, reason }` (`not_marked` counts as done). `lib/catalog/catalogEdits.ts` validates the result and builds the download file (`format: sacred-fire-songs/catalog-edits`, `version: 1`, `exported_at`).
* **Importer contract:** `docs/guides/importing-songbooks.md` (*Corrections made in the app*); `lib/catalog/importContract.ts` (`planCatalogImport`, `formatSkippedReport`, `catalogVersionKey`) implements it for TypeScript importers. Not protected by the markers: rows deleted in the app (they come back on the next import unless the importer checks) and songs merged in the app by linking (§6.19). For those an importer resolves every incoming slug with `fn_song_id_for_catalog_slug` and reads the returned song's own `catalog_slug`: none → create; the song carries the slug → write as usual, honouring its markers (this covers 'moved': a target without a slug took the source's, and the link marked its `aliases` and `catalog_slug`); the song carries another slug ('redirect') → no song-level writes (they would overwrite the surviving song's title, authors and aliases), only upsert the slug's versions under that song on `(composition_id, catalog_source_id)`, honouring their markers. A moved version whose colliding `catalog_source_id` was cleared is not findable by that key, by design. `resolveCatalogSlug(slug, found)` is that mapping; chains need no handling (the link function collapses them).
* **Focus:** after *Taken over* succeeds, the row leaves the list and focus moves to the next row's button, else the previous one, else the empty state.
* **Tests:** `docs/testing/ux-v3-protect-app-edits.feature` (`@unit`, `@seed` as the real roles), Vitest `testing/unit/tests/catalog/*`, `testing/unit/tests/schemaCatalogEdits.test.ts` (fresh-install parity).

* **Song rows (Story 6.1.2, `components/home/SongCard.tsx`):** each result is a compact row, not a card: title (`text-row`), one grey `text-meta` line `Author · Category · Language` (`songRowMeta()` in `lib/songs/songMeta.ts`: authors joined, the first non-artist, non-language tag, the first language tag), a key badge on the right, and heart + add-to-playlist as separate 44 px buttons. The whole row is a stretched link; no coloured chips, glow, accent bar or chord/melody/take icons. At 390 × 844 at least six rows are visible (`e2e/tests/ux-v2-song-rows.spec.ts`). Library lists (recently viewed, new since last visit, playlist detail) and Library → Artists use the same `ListRow` style.
